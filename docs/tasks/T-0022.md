## Goal
"不想自己读邮件". Every email synced in the last 14 days gets a Chinese summary: what it
is, whether action is needed and what, any deadline, and how important it is. Summaries
live in a new `email_summary` table.

How it runs:
- The work is a `summaries.email` job. It is queued after every successful sync (each
  source already syncs on its own schedule) and on request; it has no schedule of its own.
- Verification-code, OTP and password-reset mail is marked `skipped_sensitive` and never
  sent.
- If the key is missing or rejected, the account is out of balance, or the month's budget
  is used up, mail waits as `pending` and `GET /summaries/status` says why.
- The Hub serves `GET /models/usage`, `GET /summaries/email?item_ids=…`,
  `GET /summaries/status` and `POST /summaries/run`.

## Out of scope
- The web UI and the 今日 page (T-0023). Buttons to re-summarise or retry. Summarising mail
  older than 14 days.
- Any write to the mailbox. Recipients' addresses are never sent to the model.

## Acceptance (runnable)
- `uv run pytest tests/hub/test_sensitive_mail.py -q`:
  - flags all of at least 15 positive samples (163, QQ, Google, Apple, Microsoft, a bank,
    Canvas login; Chinese and English; the code in the subject or the body);
  - flags none of at least 10 ordinary mails (Canvas assignment and announcement, course
    mail, newsletter, receipt).
- `uv run pytest tests/hub/test_summaries.py -q`, with FakeProvider and a fixed clock:
  - **Normal runs:**
    - each mail gets one `ok` summary with `model_call_id` and `prompt_version`;
    - a second run makes no model call;
    - a changed mail body is summarised again; a read-state change is not.
  - **Mail that is never sent:**
    - sensitive mail is `skipped_sensitive`, and its text never reaches the provider;
    - unparsable notes and empty bodies are `skipped_unreadable`;
    - mail older than 14 days gets no row.
  - **Missing key:** no call is made, rows stay `pending`, blocked=`no_key`. Skipping
    still applies.
  - **Budget used up:** the run stops before the call, rows stay `pending`,
    blocked=`budget` with notice 「本月 AI 预算已用完」. The next UTC month resumes.
  - **Provider errors:**
    - 401/402/429 stop the run without burning attempts;
    - 500 and bad JSON retry after 5 min, then after 10 min, then become `failed`;
    - bad_request fails at once.
  - **Limits and triggers:**
    - a run handles at most 20 mails and queues a continuation when more remain;
    - a successful sync queues exactly one summary job (idempotency key);
    - deleting the integration removes its summaries.
  - Another owner's mail and summaries never appear.
- `uv run python scripts/verify/hub.py summaries` exits 0. It runs the real Hub with
  `POS_MODEL_PROVIDER=fake`, a fake IMAP server and three mails (a Canvas deadline,
  「您的验证码是 482913」, a newsletter), and checks:
  - **Before the key:** status `no_key`, the OTP mail is already `skipped_sensitive`,
    and there are no `model_call` rows.
  - **After `PUT /credentials/deepseek` and `POST /summaries/run`:** two `ok` summaries
    and two `model_call` rows with cost > 0. `482913` is not in the fake model log, the
    Hub log, or any table except `synced_item` (the mailbox copy, which stores the body).
  - **Re-sync:** no new `model_call`.
  - **Budget:** after a restart with `POS_AI_BUDGET_USD=0.000001`, a new mail stays
    `pending` with notice 「本月 AI 预算已用完」 and no new call.
  - **Key:** it appears in no response, in no byte of `hub.sqlite*` and in no log.
- `uv run python -m tools.check` exits 0, with `apps.hub.summaries` in both import-linter
  contracts and `openapi.json` regenerated.
- 未验证: how many sensitive mails the filter catches in the user's real 163 mailbox.
  Spike (≤ 15 min, after 163 is connected and before the key is entered): look through
  the summaries. Skipped mail is labelled; any OTP mail still `pending` is a miss to add to
  the test samples.
