## Goal
The email half of the brief ("不想自己读邮件"). The user's mailbox is a NetEase 163 address
now and will be Gmail later. One read-only IMAP connector serves both: the Hub syncs new
mail in the background (sender, subject, time, text, attachment names, read state) without
ever changing the mailbox.

## Out of scope
- Sending, deleting, moving or marking mail (never here; sending is P3).
- Gmail OAuth (an app password works through this connector); summaries by a model.

## Acceptance (runnable)
- `uv run pytest tests/hub/test_email.py -q` against a local fake IMAP server: messages
  with sender, subject, time, text and attachments; nothing changed on the server
  (EXAMINE, BODY.PEEK, no STORE/EXPUNGE); the `ID` command 163 requires comes before the
  mailbox is opened; the next sync reads only new mail; a backlog is read oldest first
  over several syncs; a huge, mislabelled or unparsable message is stored, not fatal; a
  refused message or dropped connection keeps the cursor before it, and a message refused
  on 3 syncs becomes a note so later mail still arrives; two mails sharing a Message-ID
  are both kept; read state follows
  the mailbox; a renumbered folder does not duplicate mail;
  a wrong code says to use the 授权码; settings are validated (TLS required off this PC,
  no secrets in config); the code is in no response, table, log or audit row.
- `uv run python scripts/verify/hub.py email` exits 0 against the real Hub.
- `pnpm run typecheck`, `pnpm run test`, `uv run python scripts/verify/web.py` and
  `uv run python -m tools.check` exit 0; the 连接 page has an email form and 最近邮件.
- 未验证 until the user connects: the real 163 server (IMAP enabled, the 授权码, the `ID`
  requirement). Spike: the user turns on IMAP, creates a 授权码 and connects (≤ 15 min).

## Errors & lessons
- Review found silent mail loss (newest-first batches skipped the oldest, large messages
  and bad charsets failed the whole sync) and a stale read state. Fixed by oldest-first
  batching, size-aware fetches, per-message fallbacks and read-state patches.
- Re-review found that one permanently refused message blocked all later mail while the
  status said ok, and that a reused Message-ID could overwrite another mail. Fixed with a
  retry limit per message and receive time in the id.
