## Goal
The second foundation for the email and Canvas integrations. They need a token or
password; the Hub must keep it:
- only in Windows Credential Manager (keyring), never in SQLite, files, logs, audit or
  exports;
- writable and deletable by the user, but never readable back over HTTP;
- readable by Hub modules (job handlers) through `credentials.service`, each use audited.

## Context / inputs
- HANDOFF §4.6: credentials live in Windows Credential Manager via `keyring`.
- HANDOFF §4.7: on a new PC the user re-enters credentials; exports carry none.
- ADR 0014 D4: until S8 any local process can call the Hub; writing a credential is the
  same accepted local-only gap, and reading one back is impossible by design.

## Out of scope
- OAuth flows and real providers (T-0012 and the connector cards, after the user picks
  the mailbox and Canvas).
- A web page for entering credentials (with the integrations UI).

## Acceptance (runnable)
- `uv run pytest tests/hub/test_credentials.py -q` passes, covering:
  - PUT stores the secret in the secret store and only metadata in SQLite; GET lists
    names and dates but no secret; there is no route that returns a secret;
  - the secret is in no table, audit row, response, log line or export;
  - overwrite and delete work (delete removes it from the store); a bad name is 422;
  - `service.reveal` returns the secret to Hub code, audits the use, and raises NotFound
    for an unknown or deleted name; a metadata row whose secret vanished from the store
    reads as missing;
  - owner scoping; one audit event per write.
- `uv run python scripts/verify/hub.py credentials` exits 0 against the real Hub with a
  throwaway keyring service name: the secret reaches Windows Credential Manager, is in no
  byte of hub.sqlite* or the Hub log, and is gone after DELETE.
- `uv run python -m tools.export_openapi --check` and `uv run python -m tools.check` exit 0.
