## Goal
First step of the user's multi-model AI platform (ADR 0028, phase 6 of ADR 0026). Vendor
calls go through LiteLLM, so new vendors (Qwen, GLM, Kimi, OpenAI, Gemini, …) need only a
price entry and a name, not a hand-written adapter. LiteLLM sits behind
`ModelProvider`. Business code and the `models.service` guarantees do not change:
- the budget is checked before the call;
- one `model_call` row per call, at our own dated peak prices;
- the key comes only from Credential Manager;
- no text is stored, no key is logged, redirects are never followed.

## Out of scope
- Second vendor, model registry, benchmark, workflow router, memory gateway: later cards,
  after real email data (the user's order).
- The LiteLLM proxy server. Only the Python SDK is used.

## Acceptance (runnable)
- `litellm-core==1.106.6` (uploaded 2026-10-28, ≥ 14 days old, MIT) is pinned in
  `pyproject.toml`. It is the lighter distribution without boto3, tokenizers or
  huggingface-hub.
- `uv run pytest tests/hub/test_models.py -q` passes. The whole T-0021 suite now runs
  against `LiteLLMProvider` on the same local stub:
  - request shape;
  - usage, including cached tokens;
  - 401/402/429/500/400 mapping;
  - timeout;
  - bad output, including a 200 with an HTML body;
  - missing usage charged at the estimate;
  - budget refusal before any request;
  - concurrent reservations;
  - the key never in rows, logs, repr or errors;
  - a 302 to another host sends nothing there.
- A new test: with LiteLLM's loggers switched to DEBUG, neither the mail text nor the key
  appears in logs, stdout or stderr, and the bundled cost map is used (no download).
- `uv run python scripts/verify/models.py` exits 0 (offline, real migrations, stub).
- `.evidence/T-0024/spike.log`: what LiteLLM 1.106.6 does against the stub (request
  body, usage, error types, no redirect follow, debug-log behaviour).
- `uv run python -m tools.check` exits 0.
- 未验证: a live call through LiteLLM to api.deepseek.com. Spike: `--live` after the user
