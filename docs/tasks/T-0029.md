## Goal
On 2026-11-11 at about 17:30, the supervisor and the Hub were stopped by STATUS_CONTROL_C_EXIT
(0xC000013A). The task's restart-on-failure settings did not start them again, and the Hub
stayed down until the assistant started the task by hand. Fix this: the logon trigger repeats
every 5 minutes, forever, so a killed supervisor comes back within 5 minutes. A running one
is left alone (`MultipleInstances IgnoreNew`).

## Constraints
- While update-hub.ps1 or install-always-on.ps1 replaces the copy, the watchdog must not
  start the Hub from half-built files. They write `<data>\updating.lock`, and run-hub.ps1
  waits while it is held: only while the updating process runs, never more than 60 minutes.
- The classifier blocks the assistant from registering the task, so the user runs
  install-always-on.ps1 once.

## Acceptance (runnable)
- The three scripts parse. The lock functions behave as follows: no lock → no wait; a stale
  lock (holder gone, or older than 60 min) is ignored; a held lock waits until its holder
  exits; a script never frees another process's lock (`.evidence/T-0029/lock-test.log`,
  `parse.log`).
- `uv run python -m tools.check` exits 0.
- After merge: `update-hub.ps1` prints `Hub is up`; then the user runs install-always-on.ps1,
  and `uv run python scripts/verify/always_on.py --expect-task --watchdog` exits 0: the
  trigger repeats at PT5M with no end, and after the supervisor and the Hub are killed, the task brings
  them back within 6 minutes.
